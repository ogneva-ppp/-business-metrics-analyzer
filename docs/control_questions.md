# Ответы на контрольные вопросы (ПЗ № 1)

## 1. Чем отличается Git от GitHub?

**Git** — распределённая система контроля версий. Она устанавливается на компьютер, хранит историю изменений проекта и работает локально, без интернета.

**GitHub** — облачная платформа, на которой хранятся Git-репозитории. Она добавляет совместную работу: удалённое хранилище, Pull Request, ревью кода, права доступа, Issues, Projects.

Git — инструмент, GitHub — сервис, который использует этот инструмент. Git можно использовать без GitHub (есть также GitLab, Bitbucket).

## 2. Для чего используется виртуальное окружение Python?

Виртуальное окружение (`venv`) — изолированная среда с собственным интерпретатором и набором библиотек. Оно нужно, чтобы:

- не смешивать зависимости разных проектов (например, разные версии pandas);
- не засорять системный Python;
- воспроизводимо переносить проект на другой компьютер: список библиотек фиксируется в `requirements.txt` (`pip freeze > requirements.txt`) и устанавливается командой `pip install -r requirements.txt`.

## 3. Что такое commit, branch, remote, pull request?

- **Commit** — фиксация изменений в истории проекта с сообщением, автором и уникальным идентификатором (хешем).
- **Branch** — отдельная ветка разработки. В ней можно вести работу (новую функцию, исправление), не затрагивая основную ветку `main`.
- **Remote** — удалённый репозиторий, связанный с локальным (по умолчанию называется `origin`). Обмен идёт командами `push` и `pull`.
- **Pull Request (PR)** — запрос на слияние изменений из одной ветки в другую. В PR участники обсуждают изменения, оставляют комментарии, проводят ревью, после чего выполняется merge.

## 4. Зачем нужен файл .gitignore?

В нём перечислены файлы и папки, которые Git не должен отслеживать и отправлять в репозиторий: виртуальное окружение (`.venv/`, `venv/`), кэш (`__pycache__/`, `*.pyc`), файлы настроек IDE (`.idea/`, `.vscode/`), секреты (`.env`), временные и большие файлы данных (`*.csv`, `*.xlsx`, `*.log`).

Это уменьшает размер репозитория, не даёт попасть в него паролям и токенам и исключает лишние конфликты между участниками команды.

## 5. Как организовать командную работу над бизнес-приложением с помощью Git?

1. Создать общий репозиторий на GitHub, добавить участников (Collaborators) и описать проект в `README.md`.
2. Ветка `main` — стабильная версия. Прямые коммиты в неё не делаются.
3. Каждая задача выполняется в отдельной ветке (`feature/название`): ветка создаётся от актуального `main` (`git pull`, затем `git checkout -b`).
4. Изменения фиксируются небольшими коммитами с понятными сообщениями и отправляются командой `git push`.
5. По окончании работы создаётся Pull Request в `main`, назначается ревьюер.
6. Коллега проверяет код, оставляет комментарии; после исправлений выполняется merge.
7. Все участники регулярно обновляют локальный `main` командой `git pull origin main`.
8. Задачи и требования ведутся в Issues / GitHub Projects, документация — в `README.md` и папке `docs/`.

## 6. Какие файлы обязательно должны быть в репозитории учебного проекта?

- `README.md` — описание проекта: название, бизнес-задача, технологии, инструкция по запуску, автор;
- `.gitignore` — список исключений;
- `requirements.txt` — зависимости проекта;
- `main.py` — точка входа в программу;
- `docs/business_requirements.md` — бизнес-требования (по структуре проекта и домашнему заданию);
- папка `src/` с модулями (`analytics.py`, `config.py`) — по рекомендуемой структуре.

Не должны попадать в репозиторий: виртуальное окружение, `.env`, кэш и файлы IDE.

## 7. Что произойдёт, если два разработчика изменят один и тот же файл в разных ветках?

Если изменены **разные места** файла, Git объединит правки автоматически при слиянии.

Если изменены **одни и те же строки**, при слиянии возникнет **конфликт слияния (merge conflict)**. Git остановит merge и пометит спорные участки в файле маркерами `<<<<<<<`, `=======`, `>>>>>>>`. Разработчик должен:

1. открыть файл и вручную выбрать или объединить нужный вариант, удалив маркеры;
2. выполнить `git add <файл>`;
3. завершить слияние коммитом (`git commit`).

Чтобы конфликтов было меньше, ветки делают короткими, часто подтягивают актуальный `main` и распределяют задачи так, чтобы участники работали с разными файлами.
