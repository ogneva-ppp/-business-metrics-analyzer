# Ответы на контрольные вопросы (ПЗ № 2)

## 1. Чем отличаются бизнес-требования от функциональных и нефункциональных?

**Бизнес-требования** описывают, чего организация хочет достичь: цели, показатели, ограничения (например, сократить время подготовки отчёта с 2–3 дней до нескольких минут).

**Функциональные требования** описывают, что система должна делать: конкретные функции (например, формировать отчёт за выбранный период).

**Нефункциональные требования** описывают, как система должна работать: производительность, безопасность, удобство, надёжность (например, пересчёт KPI не более 3 секунд).

Бизнес-требования отвечают на вопрос «зачем», функциональные — «что», нефункциональные — «как хорошо».

## 2. Каким критериям должна соответствовать качественная User Story?

Критериям INVEST:

- **Independent** — независимая от других историй;
- **Negotiable** — обсуждаемая, не жёсткое техническое задание;
- **Valuable** — ценная для пользователя или бизнеса;
- **Estimable** — можно оценить трудоёмкость;
- **Small** — достаточно небольшая, чтобы уложиться в спринт;
- **Testable** — проверяемая, есть критерии приёмки.

Формат: «Как <роль>, я хочу <действие>, чтобы <ценность>».

## 3. Зачем нужны критерии приёмки и как они связаны с тестированием?

Критерии приёмки определяют условия, при которых User Story считается выполненной. Они устраняют разночтения между заказчиком, аналитиком и разработчиками и фиксируют ожидаемый результат до начала разработки.

С тестированием они связаны напрямую: каждый критерий в формате Given-When-Then превращается в тест-кейс (Given — подготовка, When — действие, Then — проверка результата). Если все критерии выполнены, история принята.

## 4. Какие элементы включает Use Case-диаграмма?

- **акторы** — роли, взаимодействующие с системой (пользователи или внешние системы);
- **варианты использования (Use Cases)** — функции, которые система выполняет для актора;
- **границы системы** — прямоугольник, внутри которого находятся варианты использования;
- **связи** — ассоциации актор–вариант использования, а также отношения include (включение) и extend (расширение).

## 5. Что такое backlog и как он приоритизируется?

Backlog — упорядоченный список задач проекта (User Stories, доработок, исправлений). Он постоянно уточняется, и верхние задачи наиболее приоритетны.

Приоритизируют по бизнес-ценности, например:

- **MoSCoW**: Must have, Should have, Could have, Won't have;
- MoSCoW вместе с оценкой в Story Points;
- матрица «ценность / сложность».

После приоритизации задачи распределяются по спринтам.

## 6. Как связаны User Stories, Use Cases и backlog?

Бизнес-требования раскладываются на User Stories, и каждая история даёт ценность конкретной роли. Use Cases показывают, как акторы взаимодействуют с системой, и соответствуют группам историй (каждому варианту использования отвечает одна или несколько историй). Backlog собирает все User Stories в один список с приоритетом, оценкой и спринтом.

Цепочка: бизнес-требование → User Story → Use Case → задача в backlog → разработка и тестирование по критериям приёмки.

## 7. Какие методы сбора требований вы знаете? В каких ситуациях они применяются?

- **Интервью** — для уточнения целей и деталей с заказчиком и ключевыми пользователями;
- **Анкетирование** — когда нужно собрать мнения большого числа пользователей;
- **Наблюдение** — для изучения реального процесса работы (AS-IS), который люди не всегда могут описать словами;
- **Анализ документов и существующих систем** — когда есть регламенты, отчёты, старое ПО;
- **Мозговой штурм и воркшопы** — для генерации идей и согласования требований командой и заказчиком;
- **Прототипирование** — когда требования неясны и нужно показать пример интерфейса;
- **Анализ вариантов использования и User Stories** — для формализации собранных требований.
