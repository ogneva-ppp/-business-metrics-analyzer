# ADR-002. Выбор системы управления базами данных PostgreSQL

## Статус

Принято (на этапе архитектурного проектирования).

## 1. Контекст

В рамках проекта Business Metrics Analyzer разрабатывается веб-приложение для анализа продаж торговой компании, расчёта ключевых показателей эффективности (KPI) и формирования аналитических отчётов.

Для обеспечения работы приложения необходимо организовать централизованное хранение данных о продажах, пользователях, настройках метрик и результатах аналитических операций.

При выборе системы управления базами данных учитываются следующие требования:

- обработка данных объёмом до 1 млн записей о продажах;
- время отклика дашборда не более 3 секунд;
- поддержка одновременной работы пользователей с различными ролями;
- обеспечение целостности данных при импорте CSV, Excel и обработке запросов;
- интеграция с Python, FastAPI и SQLAlchemy;
- возможность развёртывания приложения в Docker;
- перспективы дальнейшего масштабирования системы.

В качестве основных вариантов рассматриваются PostgreSQL и SQLite.

## 2. Решение

Для Business Metrics Analyzer выбрана реляционная система управления базами данных PostgreSQL.

Выбор PostgreSQL обусловлен следующими преимуществами:

1. **Поддержка транзакций.** PostgreSQL обеспечивает атомарность операций и возможность отката изменений при возникновении ошибок во время импорта данных.
2. **Обработка больших объёмов информации.** СУБД предоставляет средства индексирования и оптимизации запросов, необходимые для эффективной работы с данными о продажах.
3. **Многопользовательский доступ.** PostgreSQL позволяет одновременно обрабатывать запросы нескольких пользователей.
4. **Интеграция с Python.** Использование SQLAlchemy обеспечивает взаимодействие приложения с базой данных и упрощает реализацию паттерна Repository.
5. **Поддержка Docker.** PostgreSQL может развёртываться в отдельном контейнере, что упрощает настройку и перенос системы между средами.
6. **Возможность развития.** СУБД поддерживает расширение структуры данных и дальнейшую оптимизацию производительности.

В проектируемой архитектуре PostgreSQL размещается в отдельном Docker-контейнере на основе образа `postgres:16`.

Приложение FastAPI взаимодействует с PostgreSQL для получения и сохранения данных. Для ускорения повторных запросов к аналитическим показателям дополнительно предусматривается использование Redis.

## 3. Альтернативы

### 3.1. SQLite

**Преимущества:**
- простая настройка;
- отсутствие необходимости запуска отдельного сервера базы данных;
- низкие требования к ресурсам;
- удобство использования в небольших приложениях и прототипах.

**Недостатки:**
- ограничения при интенсивной одновременной записи данных;
- менее удобная организация централизованного многопользовательского доступа;
- дополнительные сложности при масштабировании серверного приложения.

SQLite подходит для небольших проектов, однако PostgreSQL лучше соответствует требованиям Business Metrics Analyzer к многопользовательской работе и развитию системы.

### 3.2. MySQL

**Преимущества:**
- высокая распространённость;
- поддержка транзакций и индексов;
- возможность использования в многопользовательских веб-приложениях.

**Недостатки относительно выбранного решения:**
- переход на MySQL не предоставляет очевидных преимуществ для текущих требований проекта;
- потребует пересмотра уже согласованных архитектурных решений и документации.

MySQL является допустимой альтернативой, но в рамках данного проекта предпочтение отдано PostgreSQL.

## 4. Последствия

**Положительные последствия:**

- Обеспечивается централизованное хранение данных.
- Повышается надёжность операций импорта благодаря транзакциям.
- Поддерживается одновременная работа нескольких пользователей.
- Появляется возможность оптимизировать аналитические SQL-запросы.
- Обеспечивается совместимость с выбранным технологическим стеком.
- Создаётся основа для дальнейшего развития приложения.

**Отрицательные последствия:**

- Требуется настройка отдельного контейнера PostgreSQL.
- Увеличивается потребление вычислительных ресурсов по сравнению с SQLite.
- Необходимо организовать резервное копирование и контроль состояния базы данных.
- При увеличении объёма данных потребуется дополнительная оптимизация запросов и индексов.

Принятое решение соответствует требованиям проекта и обеспечивает баланс между функциональными возможностями, надёжностью и сложностью инфраструктуры.
