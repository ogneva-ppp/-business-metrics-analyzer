# ADR-004: Кэширование KPI через Redis

**Статус:** Предложено

## 1. Контекст

Business Metrics Analyzer предназначен для анализа данных о продажах и расчёта ключевых показателей эффективности (KPI), таких как выручка, прибыль, средний чек и рентабельность.

При каждом обращении к дашборду повторный расчёт KPI по большому объёму данных может создавать дополнительную нагрузку на PostgreSQL и увеличивать время ответа системы.

Согласно архитектурным требованиям, время отклика дашборда не должно превышать 3 секунд. Поэтому необходимо предусмотреть механизм ускорения повторных запросов.

Для решения этой задачи рассматривается кэширование результатов расчёта KPI с использованием Redis.

## 2. Решение

Для ускорения повторных запросов KPI предлагается использовать Redis в качестве распределённого кэша.

Механизм кэширования будет работать следующим образом:

1. Пользователь отправляет запрос на получение KPI через дашборд.
2. KPI Service проверяет наличие рассчитанного показателя в Redis.
3. Если значение найдено (cache hit), оно возвращается пользователю без повторного расчёта.
4. Если значение отсутствует (cache miss), KPI Service получает необходимые данные из PostgreSQL и рассчитывает показатель.
5. Полученный результат сохраняется в Redis с ограниченным временем жизни (TTL).
6. При изменении исходных данных о продажах соответствующие записи кэша инвалидируются (удаляются или обновляются).

Ключи кэша должны учитывать тип KPI, период расчёта и применённые фильтры, чтобы результаты разных запросов не смешивались.

При недоступности Redis система должна продолжать работу, рассчитывая KPI непосредственно по данным PostgreSQL.

Такой подход позволяет снизить нагрузку на базу данных и ускорить повторные обращения к дашборду.

## 3. Альтернативы

При выборе механизма кэширования KPI были рассмотрены следующие варианты:

| Альтернатива | Преимущества | Недостатки |
|---|---|---|
| Без кэширования | Простая архитектура, данные всегда рассчитываются по актуальной информации из PostgreSQL | Высокая нагрузка на базу данных при повторных запросах |
| Кэширование в памяти Python | Высокая скорость доступа, не требуется дополнительный сервис | Данные кэша теряются при перезапуске приложения; кэш не является общим для нескольких экземпляров сервиса |
| Redis | Быстрый доступ к результатам, поддержка TTL, возможность использования общего кэша несколькими экземплярами приложения | Требует дополнительной инфраструктуры и механизма инвалидации устаревших данных |

Предпочтительным вариантом выбран Redis, поскольку он позволяет ускорить повторные запросы KPI и поддерживает масштабирование приложения. При этом необходимо предусмотреть управление временем жизни записей и их инвалидацию при изменении исходных данных.

## 4. Последствия

### Положительные последствия

- Сокращение времени ответа на повторные запросы KPI.
- Снижение количества повторных вычислений и нагрузки на PostgreSQL.
- Возможность использовать общий кэш несколькими экземплярами приложения.
- Поддержка автоматического удаления устаревших записей с помощью TTL.

### Отрицательные последствия и риски

- Необходимость развёртывания и сопровождения дополнительного сервиса Redis.
- Возможность получения устаревших показателей при неправильной инвалидации кэша.
- Дополнительное потребление оперативной памяти.
- Усложнение диагностики ошибок и тестирования.

### Меры по снижению рисков

- Устанавливать ограниченное время жизни кэшируемых значений (TTL).
- Инвалидировать соответствующие ключи при изменении данных о продажах.
- При недоступности Redis выполнять расчёт KPI непосредственно через PostgreSQL.
- Контролировать время ответа дашборда и долю успешных обращений к кэшу.

Использование Redis должно способствовать выполнению требования по времени отклика дашборда до 3 секунд, однако соответствие этому требованию необходимо подтвердить нагрузочным тестированием.
