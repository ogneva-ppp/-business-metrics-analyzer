# ADR-003. Выбор способа аутентификации (JWT vs сессии)

## Статус
Принято

## Контекст
«Business Metrics Analyzer» — веб-приложение с четырьмя ролями (коммерческий директор, менеджер по продажам, аналитик, администратор). Нефункциональные требования: аутентификация по JWT, разграничение ролей (драйвер AD-02), время отклика дашборда не более 3 с (AD-01). Приложение развёртывается в Docker, API построен на FastAPI и может запускаться в нескольких экземплярах; возможен переход к микросервисам.

## Решение
Использовать аутентификацию по JWT. При входе `AuthService` проверяет пароль (хеш) и через `JwtProvider` выпускает короткоживущий access-токен (роль пользователя в claims) и refresh-токен. Контроллеры проверяют токен и роль зависимостью FastAPI, обращения к БД для проверки не нужны. Токен передаётся в заголовке `Authorization: Bearer`, соединение защищено HTTPS (Nginx).

## Альтернативы
1. Серверные сессии (cookie + хранилище сессий) — просты и позволяют мгновенно отозвать сессию, но требуют общего хранилища при нескольких экземплярах приложения и обращения к нему на каждый запрос; хуже подходят для последующего перехода к микросервисам.
2. Basic-аутентификация — проще всего, но пароль передаётся в каждом запросе, нет ролей и срока действия; не подходит для требований безопасности.
3. Внешний провайдер (OAuth2/OIDC) — надёжно, но избыточно для учебного MVP и добавляет внешнюю зависимость.

## Последствия
+ Приложение не хранит состояние сессии, легко масштабируется горизонтально.
+ Роль в токене позволяет проверять права без запроса к БД, это помогает уложиться в 3 с.
+ Токен подходит и для будущих микросервисов.
− Выданный токен нельзя отозвать до истечения срока; нужны короткий срок жизни и refresh-токены.
− Нужно безопасно хранить секретный ключ подписи (переменная окружения) и ротировать его.
− Токен в браузере уязвим при XSS, поэтому нужны HTTPS и аккуратная работа с хранением токена на клиенте.
