# ADR-001. Выбор архитектурного стиля

## Статус
Принято.

## Контекст
Проект **Business Metrics Analyzer** — веб-приложение для расчёта и визуализации KPI торговой компании. Разработка ведётся небольшой командой (3–4 человека); требуется быстрый MVP с возможностью дальнейшего развития.

Архитектура должна учитывать: отклик дашборда не более 3 секунд; импорт до 1 млн записей о продажах; аутентификацию по JWT и разграничение ролей; развёртывание в облаке с использованием Docker. Основные функциональные области: пользователи, импорт, KPI, дашборды, отчёты, настройки, аудит.

## Решение
Выбран **слоистый монолит с элементами Clean Architecture**. Приложение является единым развёртываемым продуктом, а его логические части разделены на слои:

1. **Presentation** — Web UI и REST API (FastAPI).
2. **Application** — прикладные сервисы и сценарии использования.
3. **Domain** — модели и правила расчёта KPI, не зависящие от инфраструктуры.
4. **Infrastructure** — PostgreSQL, Redis, файловое хранилище, JWT и внешние интеграции.

Для быстрого получения KPI предусматривается кэширование/предрасчёт; для крупных загрузок — пакетный и асинхронный импорт. Взаимодействие между логическими сервисами в рамках монолита не требует отдельных сетевых вызовов.

## Альтернативы
1. **Микросервисы.** Плюсы: независимое масштабирование и развёртывание сервисов. Минусы: избыточная сложность инфраструктуры, сетевого взаимодействия и мониторинга для небольшого MVP.
2. **Монолит без выделенных слоёв.** Плюсы: минимальные начальные усилия. Минусы: высокая связанность, сложнее тестировать и сопровождать при росте функциональности.
3. **Serverless.** Плюсы: управление инфраструктурой частично передаётся провайдеру. Минусы: ограничения и дополнительная сложность организации длительных пакетных задач импорта.

## Последствия

**Положительные:**
- Быстрая разработка и развёртывание MVP.
- Чёткое разделение ответственности между слоями.
- Более простое тестирование бизнес-логики.
- Возможность постепенно выделять сервисы по мере роста нагрузки.

**Отрицательные:**
- Нельзя независимо масштабировать отдельные логические модули без дополнительных изменений.
- При переходе к микросервисам потребуется рефакторинг.
- Необходимо следить за границами слоёв, чтобы монолит не превратился в тесно связанный код.
